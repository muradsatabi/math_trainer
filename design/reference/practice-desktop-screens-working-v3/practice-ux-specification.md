# Практика: UX-спецификация

Проект: «Математический тренажёр».
Версия: 0.51 — все компьютерные экраны собраны с адаптацией высоты окна.
Дата обновления: 9 октября 2026 года.
Источник: решения Мурада в чатах «Дизайн и пользовательский опыт» и «Продукт и управление проектом».

Документ фиксирует принятые решения, предложения и открытые вопросы. Это основа следующих макетов, а не готовое техническое задание на реализацию. Границы ближайшей версии согласуются в продуктовом чате.

## 1. Сценарий и границы

Проектируем практические задания, которые ученик решает, чтобы научиться. Первая тема — вынесение общего множителя за скобки. Начальная аудитория — восьмиклассники; интерфейс на русском языке, без чрезмерно детского оформления.

Начинаем с адаптивной веб-версии для телефона и компьютера на Dart/Flutter. Общее входное тестирование и входное тестирование отдельной главы имеют другую логику и в текущий сценарий не входят. Печатный пилот уже начался и проходит всю подготовленную последовательность; его правила этим документом автоматически не меняются. Набор из 110 заданий не означает согласование всего набора для первой версии приложения.

### 1.1. Режимы ресурса — продуктовая фиксация

6 октября 2026 года Мурад зафиксировал следующие режимы:

- Вводная диагностика при первом входе в ресурс.
- Вводная диагностика по большому разделу.
- Вводная диагностика по теме.
- Практика.
- Экзамен (контрольная работа) по теме.
- Экзамен (контрольная работа) по разделу.

Сейчас прорабатывается только режим «Практика». Остальные режимы зафиксированы как направления развития, а не как текущая реализация; их подробные сценарии ещё не согласованы.

## 2. Принятые решения

| Пункт | Решение |
| --- | --- |
| Задание | Одно задание на экране |
| Количество заданий | Адаптивное, зависит от успешности, заранее не фиксируется |
| Показатель | Скользящий процент успешности по последним N оцениваемым заданиям |
| Продвижение | Не показываем долю пройденных заданий вроде «3 из 10» для текущей адаптивной практики; основной показатель — скользящая успешность |
| Отправка ответа | Отдельная кнопка «Проверить себя» |
| Следующее задание | После правильного ответа — кнопка «Дальше», переход только по нажатию, без автоматического перелистывания |
| Основные действия | Кнопки «Проверить себя» и «Дальше» синие; точный оттенок ещё не согласован |
| Верный ответ | Текст «Абсолютно верно!», галочка и зелёное выделение ответа |
| Неверный ответ | Временно «Пока не получилось!» в синей гамме; формулировку пересмотреть позже. Мягкое красноватое выделение и красный крестик у выбранного ответа |
| Объяснение | Объяснение того, как работает практика, занимает значимое, заметное место в интерфейсе |
| Шапка | Слева название темы (примерно 70% ширины), справа компактная успешность; шапка поднята, название немного уменьшено |
| Выравнивание шапки | «Практика» и «Успешность» — одинаковая гарнитура, размер и вес, на одной горизонтали. Одинаковый отступ под подписями; верх названия темы и верх строки индикатора с процентом выровнены |
| Варианты | Минимум четыре; текущая компоновка — четыре широкие горизонтальные строки друг под другом. Сетка 2 × 2 исключена из текущего макета |
| Выбор | Вся карточка нажимается; без кружков. Выбор обозначается заливкой и рамкой, с доступным программным состоянием для экранного диктора |
| Короткие подписи | «Вынеси общий множитель за скобки:» и «Выбери ответ:» — с двоеточием |
| Под кнопкой | Постоянную подсказку «Можно изменить выбор» / «Сначала выбери один вариант» не показываем |
| Индикатор | Компактный бар и числовой процент; глубокий оранжевый при низкой успешности, переход к зелёному при приближении к 85%; без красного |
| Изменение индикатора | После каждой оцениваемой попытки обновлять по текущей успешности: возможны рост и снижение заполнения и обратное изменение цвета. Не увеличивать за само количество выполненных заданий |
| Процент в шапке | Одинаковый размер шрифта с названием темы; выравнивание по базовой линии первой строки темы. Бар центрирован относительно процента по вертикали |
| Цвет процента | Постоянный обычный цвет текста, белый в текущей тёмной теме; не окрашивать цифры по успешности. В светлой теме использовать контрастный цвет текста |
| Цвет заполнения при 65% | Жёлто-зелёный промежуточный оттенок, ещё не окончательный зелёный. Цвет меняется только у заполнения бара |

Тексты «Молодец», «Получилось!», «Верно!», «Узнать правильный ответ» и «Решить» не являются текущими выбранными формулировками.

## 3. Адаптивное переключение формата

Отдельный документ-основание: **adaptive-answer-format-logic.md**, краткое название **«Логика 70% → 85%»**. Идентификатор сохранённого документа: libfile_ea4077c4227c8191b5f6e3804e3224f7.

| Текущая скользящая успешность | Правило |
| --- | --- |
| Ниже 70% | Выбор ответа из вариантов |
| От 70% включительно до 85% | Ввод ответа, если он возможен для данного типа задания |
| От 85% включительно | Тип заданий завершён по этому правилу |

Используется единый показатель по ответам обоих форматов. При падении ниже 70% возвращается выбор, при повторном достижении 70% — ввод. Это не фиксированные доли количества заданий и не две независимые проверки. Размер окна и детали расчёта пока не выбраны.

Процент может расти и снижаться, поскольку новые результаты заменяют старые. Он не обозначает процент освоения темы и не гарантирует устойчивого понимания. Возвращение к выбору ответа не должно выглядеть как наказание или понижение уровня ученика.

## 4. Объяснение работы ученику

Обязательное содержание объяснения:

- Что означает скользящий процент успешности: результат последних оцениваемых заданий.
- Почему процент может уменьшаться, хотя ученик продолжает работать.
- Почему количество заданий заранее не определено.
- Когда и почему выбор ответа сменяется вводом и может возвращаться обратно.
- Что означает порог завершения 85% в этой практике.

Объяснение успешности открывается по нажатию на её компактную область во всплывающем окне, а не раскрывается на основном экране. Точные тексты и поведение окна ещё проверяем на макете. Краткое объяснение перед первой практикой остаётся предложением.

### 5.1. Помощь при последовательных ошибках — принятое продуктовое правило

Согласовано Мурадом в продуктовом чате 6 октября 2026 года. Серия относится к одному конкретному виду задания, а не к ошибкам во всём ресурсе.

| Ситуация | Поведение приложения |
| --- | --- |
| Первая ошибка | Предлагается добровольно посмотреть подсказку во всплывающем окне; затем даётся аналогичное задание |
| Вторая ошибка подряд | Снова предлагается добровольная подсказка во всплывающем окне; затем даётся аналогичное задание |
| Третья ошибка подряд | Подсказка / объяснение данной конкретной ошибки становится основным содержимым экрана, а не дополнительным всплывающим окном |

Уточнение Мурада: оговорка «если он решает три» не устанавливает отдельного правила; имеется в виду именно три ошибки подряд.

Принцип утверждён; точные правила подсчёта и сброса серии, учёт повторных попыток и ошибок ввода, действие после полноэкранного объяснения и взаимодействие со скользящей успешностью пока открыты. Содержание подсказок и объяснений согласуется в методическом чате. Это решение не утверждает демонстрационные тексты макетов и не запускает разработку автоматически.

## 6. Предложения для следующего согласования

- Поведение выбранной карточки при управлении клавиатурой и после проверки.
- Крупное математическое выражение и короткая методически согласованная инструкция.
- Сохранять ответ после ошибки, чтобы не вводить всё заново.
- Предсказуемое расположение обратной связи без заметного скачка экрана.
- Сначала проработать небольшой телефон, затем компьютер с тем же порядком действий.

Все перечисленные детали остаются предложениями до согласования. Никакие аккаунты, оплата, рейтинги, персонажи, награды, ИИ-чат или другие крупные функции не добавляются без продуктового решения.

## 7. Обязательные принципы удобства и доступности

- Ввод не должен создавать дополнительную математическую трудность.
- Не использовать цвет как единственный признак состояния: дополнять словами и значками.
- Сохранять контраст текста и читаемость минусов, степеней, скобок и дробей.
- Предусмотреть удобное касание на телефоне и управление клавиатурой на компьютере; конкретное поведение ещё проектируется.
- Не объявлять пропущенные этапы освоенными автоматически и не делать вывод о понимании по одному ответу.
- Допустимые ответы, ошибки и подсказки брать из актуальной методической сводки, не придумывать в дизайне.

## 8. Что остаётся согласовать и кому передать

**Методика:** N, начало расчёта до заполнения окна, оцениваемые попытки, округление и пороги, учёт подсказок и ошибок ввода, действия после неверного ответа, допустимые записи, варианты ответов, применимость ввода.

**Продукт:** включение адаптивности и обоих форматов в ближайшую версию; границы набора заданий. Эта UX-фиксация не заменяет итоговое продуктовое согласование.

**Дизайн:** показ процента и порогов, объяснение правил, конкретное задание, ввод, переходы, компоновка, цвета и макеты для телефона и компьютера.

**Разработка:** передать согласованные экраны, состояния, действия, тексты, поведение при разных размерах экрана и критерии проверки после методического и продуктового согласования. Производственный код в этом чате не создаётся.

## 9. Вопросы для проверки на учениках

- Может ли ученик без подсказки выбрать ответ и отправить его на проверку?
- Понимает ли результат проверки по тексту и значку без опоры только на цвет?
- Может ли своими словами объяснить показатель, его снижение и переключение формата?
- Понимает ли, что процент относится к последним ответам, а не к доле освоенной темы?
- Легко ли вводить и исправлять математический ответ на телефоне?
- Различает ли сообщение о записи и сообщение о математической ошибке?
- Понятно ли следующее действие после обратной связи?

Это вопросы для проверки будущего макета, а не утверждение, что интерфейс уже удобен. Пользовательские проверки ещё не выполнены.

## 11. Текущий макет и статус согласования

Экран выбора ответа для iPhone 14 Pro: компактная выровненная шапка, четыре широкие строки, без кружков, с двоеточиями и оранжево-зелёным индикатором. Общие цвета и шрифты одобрены Мурадом; стиль универсальный для школьников, без чрезмерной детскости. Мягкая галочка согласована в макете правильного ответа 6 октября.

Для визуального сравнения используется выражение 6x + 9 и демонстрационные варианты 3(2x + 9), 3(2x + 3), 3(3x + 2), 3(2x − 3), предложенные по прямому запросу Мурада показать реальные записи. Они не являются согласованным методическим набором; учебная проверка не подключается. Значение 65% условное.

Открыто: отображать заполнение по шкале 0–100% либо относительно порога 85%; точная цветовая интерполяция, оттенки, анимация, поведение до достаточного количества результатов. Текущий эскиз использует 65% длины бара по шкале 0–100%; зелёный ориентир — 85%. Это допущение для просмотра, не новое методическое правило.

Статус: Мурад одобрил последний макет 5 октября 2026 года и поручил сохранить его. Текущий согласованный визуальный образец — **practice-screen-approved-v1.html**, экран выбора ответа до проверки. В нём процент того же размера, что название темы, выровнен с первой строкой; бар центрирован рядом. При 65% заполнение жёлто-зелёное, цифры сохраняют обычный цвет текста (белый в тёмной теме). Старые эскизы не считаются текущим согласованным дизайном.

Самостоятельный файл позволяет открыть макет повторно: работают выбор карточки и всплывающее объяснение. Это визуальный образец с демонстрационным заданием, а не приложение или реализация адаптивного оценивания. Согласование внешнего вида не закрывает методические и продуктовые вопросы выше. Короткое имя для ссылок: **«Экран практики — согласованный макет v1»**.

## 12. Согласованный экран правильного ответа

Мурад утвердил текущий макет 6 октября 2026 года. Файл: **practice-correct-approved-v1.html**. Краткое имя: **«Правильный ответ — согласованный макет v1»**.

Это состояние того же экрана после проверки, без достижения порога завершения 85%:

- Шапка, условие, выражение и все четыре строки остаются на местах.
- Все варианты заблокированы для повторного выбора.
- Выбранный правильный ответ получает мягкую зелёную заливку и рамку; справа мягкая галочка на скруглённой подложке.
- Под вариантами сообщение «Абсолютно верно!».
- На месте «Проверить себя» — синяя кнопка «Дальше»; переход только по нажатию.

Сохранённый файл конструктора обновляется с сохранением его идентичности.

### Допущения и открытые вопросы

- Выражение 6x + 9, набор символов и 75% демонстрационные. Показанное начало записи «3(2x + » изображает момент сборки; не означает автоматическую подстановку при открытии задания.

- Нужные символы не выдаются особым цветом, рамкой или ограничением количества использований.

## 21. Следующие шаги — план продолжения

Зафиксировано по запросу Мурада 7 октября 2026 года в конце сессии. Это рабочий порядок дальнейших согласований, а не утверждение предлагаемых решений или границ выпуска. Работа ведётся небольшими шагами с учётом примерно часа в день.

1. **Доработать поведение конструктора.** Начать следующую сессию с пустой строки и момента активации «Проверить себя». Затем отдельно разобрать добавление и повторное использование символов, удаление, очистку, исправление середины записи, длинные ответы и состояние после проверки. Определить нужные формы записи для текущей темы с методическим чатом; не расширять панель всеми возможностями математики заранее.
2. **Показать состояния конструктора.** Пустая строка, сборка, правильный ответ, неправильный ответ, открытое объяснение, неполная или нераспознанная запись. Использовать уже принятые рабочие экраны результата как основу; оформление новых состояний согласовать отдельно.
3. **Замкнуть переходы практики.** Показ выбора и конструктора при изменении успешности по принятому правилу 70% → 85%, уведомление о смене формата, экран завершения типа заданий и следующее действие. Правила N, оценивания, допустимых ответов, подсчёта серии ошибок и её сброса передать на согласование в методический и продуктовый чаты, не придумывать здесь. Сценарий подсказки до проверки пока остаётся отдельным открытым вопросом.
4. **Согласовать адаптацию веба к размеру окна.** Широкий компьютерный экран, узкое окно компьютера и браузер телефона; максимальная ширина, переход от двух колонок к одной, расположение объяснения, длинные формулы и увеличенный текст. Использовать существующие мобильные образцы, получив их актуальные версии. Для длинного объяснения выбрать прокрутку либо перелистывание на конкретных образцах.
5. **Доработать управление и доступность.** Касание, управление кнопками с клавиатуры, порядок и видимость фокуса, поведение фокуса после проверки, раскрытия объяснения и смены задания; доступные названия и объявления для экранного диктора. Свободный физический ввод ответа не считать уже принятым.
6. **Разобрать поведение браузера и технические состояния.** Обновление страницы, «Назад», выход и возвращение к практике; ожидание, повторные нажатия и сбои, если такие состояния нужны выбранной реализации. Что и на какой срок сохранять, согласовать с продуктом; не добавлять аккаунты или серверные функции автоматически.
7. **Проверить целостный сценарий на учениках.** Сначала отдельно согласовать, нужен ли связанный интерактивный прототип, либо достаточно доступных макетов для конкретной проверки. Проверить выбор, сборку и исправление записи, понимание успешности и переход к объяснению. Зафиксировать наблюдения и исправить обнаруженные затруднения.
8. **Подготовить спецификацию для разработчика.** Собрать актуальные экраны, состояния, действия, переходы, поведение на разных размерах, доступность и критерии проверки. Явно отметить оставшиеся методические и продуктовые зависимости. Обновлять текущий документ, сохраняя принятые решения отдельно от предложений.
9. **Перенести завершённую логику веба на Android/APK.** Использовать общие сценарии и компоненты; отдельно проверить системное «Назад», размеры касания, экранную клавиатуру при необходимости и разные размеры телефонов. Отличия вводить с понятным обоснованием. Сроки, набор функций и выпуск APK согласовать в продуктовом чате; одновременный выпуск веба и APK не предполагается.

Ближайший шаг: **пустой конструктор и доступность кнопки «Проверить себя»**. На сегодня проектирование остановлено; остальные пункты не требуют немедленного выполнения.

## 27. Что осталось до первого работающего веб-сценария

Компьютерные рабочие экраны показывают начало, решение, результаты и выход, но не являются работающим приложением или законченной логикой. Следующий порядок проработки:

1. Закрыть переходы: вход в начатую/завершённую тему, выход из незаконченной практики и возвращение, последняя ошибка в разборе, итоги без ошибок. Не определять сроки и способ сохранения без продуктового согласования.
2. Закончить поведение конструктора: пустая и неполная запись, доступность проверки, исправление, длинный ответ, результаты проверки.
3. Согласовать связь типов заданий и темы: смена формата при 70%, завершение типа при 85%, завершение всей темы и показатель в списке. Получить N, оценивание, серию ошибок и методические правила проверки из соответствующих чатов.
4. Адаптировать рабочие экраны для широкого и узкого компьютерного окна и браузера телефона, длинных объяснений и формул, увеличенного текста.
5. Проработать фокус, клавиатуру, касание, экранный диктор и необходимые состояния загрузки/сбоя браузера.
6. Подготовить согласованное учебное содержание вместо заглушек и спецификацию для разработки. Связанный прототип согласовать отдельно, если нужен для проверки.
7. В чате разработки собрать веб-сценарий; проверить на учениках, исправить выявленные затруднения. Android/APK — после завершения логики веба, выпуск отдельно согласовать.

Рекомендуемый следующий вопрос: действие при выборе уже начатой темы и сохранение незаконченной практики.


## 28. Возвращение в незавершённую практику

9 октября 2026 года Мурад согласовал продолжение с того места, где ученик остановился.

- При повторном открытии незавершённой темы возвращаем текущее задание, а не начинаем практику заново.
- До проверки сохраняем выбранный вариант либо собранную запись. Если ответа ещё нет, возвращаем пустое состояние.
- После проверки сохраняем результат: выбранные варианты заблокированы, доступно дальнейшее действие. Само возвращение не вызывает повторной проверки.
- Правило общее для выбора и конструктора, широкого и узкого веб-экрана; ту же основу предполагаем для Android. Конкретная компоновка не меняется этим решением.
- Способ хранения, срок сохранения, разные устройства и технические сбои не определены. Сохранение раскрытого объяснения и точка входа согласованы ниже. Правила оценивания и сброса серии ошибок не меняются.

Критерии проверки: выход и возврат не теряют ответ; проверенное задание не оценивается повторно; проверенный и непроверенный ответы восстанавливаются в соответствующих состояниях.


### 28.1. Прямой вход в начатую тему

9 октября 2026 года Мурад согласовал: нажатие на начатую незавершённую тему в списке сразу открывает сохранённое задание. Стартовый экран пропускается; он нужен перед первым началом практики по теме. Правило одинаково для веба на компьютере и телефоне; ту же основу переносим на Android.

Критерий проверки: незавершённая практика возобновляется без дополнительного нажатия «Начать практику», с ранее согласованным восстановлением ответа и результата. Поведение завершённой темы и выхода из практики уточняется отдельно; открытое объяснение сохраняется по разделу 28.2.


### 28.2. Восстановление открытого объяснения

9 октября 2026 года Мурад согласовал: если ученик вышел из незавершённой практики с открытым объяснением, при возвращении объяснение остаётся открытым. Правило относится как к добровольному разбору в правой области после первой или второй ошибки, так и к подробному разбору под сохранённой шапкой после третьей ошибки подряд.

Возвращаем показанное состояние вместе с заданием, ответом и результатом проверки. Само восстановление не является новой ошибкой или повторной оценкой. Основное действие продолжения остаётся доступным по ранее согласованным правилам. Правило общее для веба на компьютере и телефоне и предполагаемого переноса на Android.

Критерий проверки: при выходе с открытым разбором и возвращении ученик снова видит соответствующее объяснение, без повторного запроса. Позиция прокрутки объяснения сохраняется по разделу 29; выбор прокрутки или перелистывания длинного разбора по-прежнему открыт.


## 29. Выход, итоги и границы разбора — согласованные переходы

9 октября 2026 года Мурад согласовал кнопку выхода, затем подтвердил все пять вопросов пакета. Эти решения уточняют предыдущие рабочие макеты; сами макеты ещё требуют соответствующего обновления.

| Ситуация | Действие и состояние |
| --- | --- |
| Выход посреди практики | В шапке добавляем «К темам». Нажатие сразу возвращает к списку без подтверждения, состояние практики сохраняется |
| Возвращение к открытому объяснению | Сохраняем также позицию прокрутки, чтобы продолжить чтение с того же места |
| Нажатие на завершённую тему | Открываются итоги, откуда доступен переход к разбору ошибок при их наличии |
| Последняя ошибка в разборе | Вместо «Следующая ошибка» основное действие «К итогам» |
| Итоги без ошибок | «Разобрать ошибки» отсутствует; показываем «В этой практике ошибок не было». Не предлагаем разбирать несуществующие ошибки |

- Общие действия одинаковы для веба на компьютере и телефоне; предполагаются и для Android. Размещение кнопки в компактной шапке и поведение при узком окне нужно проверить на обновлённых макетах.
- Выход сохраняет задание, выбранный либо собранный ответ, результат проверки и открытый разбор. Возвращение не проверяет и не оценивает ответ заново.
- В разборе из одной ошибки сразу показывается «К итогам», а «Назад» неактивна.
- На завершённой теме открываются её собственные итоги; при отсутствии ошибок действие разбора не отображается.
- Восстановление прокрутки не скрывает возможность продолжения; все основные действия доступны клавиатурой и касанием после проработки фокуса.
- Срок и способ хранения, разные устройства, браузерные «Назад» и обновление страницы ещё не согласованы. Эти переходы не определяют правила завершения всей темы и расчёта её показателя.

Дальнейший шаг — поведение конструктора ответа; обновление рабочих макетов по согласованной навигации остаётся отдельной задачей.


## 30. Конструктор: начальное состояние и проверка

9 октября 2026 года Мурад подтвердил все четыре правила пакета:

1. В новом задании строка ответа пустая: заранее подставленных символов нет. Это относится к новому заданию; возвращение к сохранённому заданию восстанавливает его ответ по разделу 28.
2. Пока строка пуста, «Проверить себя» неактивна. Условия активации для непустой, неполной и нераспознанной записи уточняются следующим пакетом.
3. «Очистить» сразу удаляет всю собранную запись без дополнительного подтверждения. На пустой строке действие остаётся активным и не изменяет состояние по разделу 31.
4. После математической проверки блокируем добавление символов, удаление и очистку. Собранный ответ сохраняется с результатом до перехода дальше; повторная отправка исключена. Состояние неполной или нераспознанной записи не определено как математический результат этим правилом.

Правила общие для веба компьютера и телефона и предполагаемого переноса на Android. Расположение компонентов сохраняет рабочую основу, новые состояния требуется показать на обновлённых макетах.

Критерии проверки: новое задание не содержит демонстрационного начала ответа; пустой ответ невозможно отправить; очистка возвращает пустое состояние с неактивной проверкой; после результата все способы изменения записи заблокированы, при следующем задании доступны вновь. Клавиатура, фокус и доступные объявления ещё проектируются.


## 31. Конструктор: пустая строка, длинный ответ и неполная запись

9 октября 2026 года Мурад ответил на пакет: 1 — нет, 2 — да, 3 — да.

- До результата математической проверки «Удалить символ» и «Очистить» остаются активными даже при пустой строке. Нажатие на пустой строке ничего не меняет и не вызывает ошибку. Это не меняет неактивность «Проверить себя» при пустом ответе или блокировку редактирования после результата.
- Длинный ответ прокручивается горизонтально внутри строки. Размер математических символов сохраняется; запись не уменьшаем ради помещения в поле. Поле не растягивает страницу и не перекрывает управление. Автоматическое перемещение к месту вставки и исправление середины записи ещё уточняются.
- Если запись неполная или не распознана, сохраняем её доступной для исправления и показываем сообщение рядом с полем. Красное состояние математической ошибки не показываем. Мурад пояснил смысл: ученик не закончил запись, ему нужно дописать её. Рабочий текст для неполной записи: «Ты не закончил запись. Допиши ответ». Текст для другого вида нераспознанной записи ещё предстоит уточнить; не называть всякую такую запись неполной.
- Какие записи допустимы, признаки неполноты и влияние на оценивание/успешность определяют методический и продуктовый чаты. Эти решения задают интерфейс исправления, не формулу подсчёта.

Общая основа сохраняется на широком и узком веб-экране и при переносе на Android. Горизонтальная прокрутка относится к полю ответа, не всей странице.

Критерии проверки: удаление из пустой строки безопасно; длинная запись читается в исходном размере и целиком доступна прокруткой; при неполной записи сохраняется весь ответ, доступно редактирование, отображается понятное сообщение. Математическое неверное решение и незавершённая запись различаются текстом и поведением. Фокус и доступное объявление сообщения предстоит проработать.


## 32. Конструктор: курсор и исправление середины записи

9 октября 2026 года Мурад подтвердил все три правила пакета:

- Нажатием в строке ответа можно поставить курсор между символами, в том числе в середине. Следующее нажатие кнопки символа вставляет его в выбранное место, а не всегда в конец.
- «Удалить символ» удаляет символ слева от курсора. В конце строки удаляется последний символ. В начале строки и на пустой строке действие не изменяет запись.
- После добавления или удаления автоматически показываем место курсора в горизонтально прокручиваемом поле, сохраняя размер символов.

Эти правила уточняют ранний демонстрационный редактор из раздела 20, где добавление и удаление были только в конце. Свободный набор выражения физической клавиатурой этим не вводится: основа — кнопки символов. После результата проверки редактирование блокируется по разделу 30.

Общая основа одинакова в вебе компьютера и телефона и предполагаемом Android. Клавиатурное перемещение курсора, точность касания, восстановление позиции курсора при возвращении и выделение диапазона пока не согласованы.

Критерии проверки: вставка в середине сохраняет символы до и после курсора; удаление убирает только соседний символ слева; в начале строки ничего не удаляется; место редактирования остаётся видимым при длинном ответе. Состояния курсора нужно показать на обновлённом макете и проверить на учениках.


## 33. Конструктор: полнота записи и состояния результата

9 октября 2026 года Мурад уточнил пакет: 1 — нет, кнопка активна только после полноты выражения; 2 и 3 — да.

### До проверки

- «Проверить себя» не становится активной после первого символа. Она доступна только когда запись полная; при пустой и неполной записи неактивна.
- Полнота записи не означает математическую правильность ответа. Математический результат определяется только после отдельного нажатия кнопки. Не раскрывать правильность через доступность кнопки.
- Что считать полной и распознаваемой записью, формально согласовать в методическом чате и передать в разработку. Правила парсинга не придуманы здесь.
- Принятые сохранение записи, возможность исправления и рабочее сообщение о неполноте остаются. Когда именно показывать сообщение при недоступной проверке, предстоит согласовать. Ошибку распознавания отличать от математического неверного ответа.

### После проверки

- Правильный собранный ответ: зелёное выделение строки, галочка, справа «Абсолютно верно!», основная кнопка «Дальше».
- Неправильный собранный ответ: мягкое красноватое выделение строки, крестик, справа «Пока не получилось!» и «Узнать, как правильно», основная кнопка «Дальше».
- Объяснения используют ту же основу: после первой и второй ошибки добровольное открытие справа, после третьей подряд автоматический подробный разбор всей рабочей области под шапкой. Правила подсчёта серии и оценивания остаются за методикой и продуктом.
- Запись сохраняется, редактирование и повторная отправка после результата заблокированы по ранее согласованным правилам; компоновка элементов не скачет при проверке.

Правила общие для веба компьютера и телефона и предполагаемого Android. Состояния нужно отобразить на обновлённых макетах.

Критерии проверки: пустую и неполную запись нельзя отправить; полный неверный ответ можно отправить так же, как полный правильный; состояние кнопки не выдаёт ответ; результаты различимы по тексту и значку, не только цвету; восстановление после выхода не оценивает ответ повторно.


## 34. Сообщение о неполноте и восстановление курсора

9 октября 2026 года Мурад подтвердил все три вопроса пакета:

Критерии проверки: широкое окно используется содержимым; название, формулы и управление читаемы; длинные строки и большие промежутки не нарушают связность; пропорции и положение основных действий сохраняют узнаваемую основу; при увеличении текста и изменении окна элементы не перекрываются и не обрезаются. При высоте до 840 и до 680 CSS-пикселей уменьшаются вертикальные отступы, внутренние поля и интервалы; шрифты не уменьшаются масштабированием всего экрана. Длинное содержимое допускает прокрутку, без обрезания действий. Подробное объяснение сохраняет шапку, три шага и кнопку «Кажется, я понял»; уточнены гибкие столбцы текста и формул. Экран закрепления сохраняет исходное выражение над тремя строками навыков. Итоги сохраняют акцент 85%+; демонстрационные числа не меняют правила оценивания.

Порядок комплекта: темы → старт → задание → правильный ответ → неправильный ответ → объяснение справа → конструктор → подробное объяснение → закрепление → итоги → разбор ошибок. Это порядок просмотра состояний, а не обязательная линейная последовательность прохождения.

Критерии просмотра: открыть отдельный HTML в браузере при масштабе 100%; проверить окна 1024×768, 1366×768 и 1920×1080, учитывая, что полезная высота ниже физической высоты монитора. Проверить читаемость формул, доступность нижних кнопок, неизменность порядка блоков, отсутствие искусственной прокрутки от фиксированной минимальной высоты. Если текст не помещается, всё содержимое должно оставаться доступным прокруткой. Структура HTML и целостность архива проверены; автоматической визуальной проверки в браузере не было.
