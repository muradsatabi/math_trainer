# Публикация утверждённых шаблонов

Техническая процедура подготовлена 1 ноября 2026 года по цели владельца. Пока она не опубликована в основном GitHub и не выполнена из методического чата, сквозная автоматизация не считается настроенной.

## Канонический формат

Банк содержит `bank/templates/*.json`, схема — `bank/template.schema.json`. Здесь хранятся шаблоны, а не постоянные экземпляры заданий. Статус `active` означает доступность реализации; `deferred` — отложено; `review` — отдельно не утверждено. Методическое состояние указано в `methodical_status`. Опубликованность определяется принятым коммитом, не заменяет методическое утверждение и не кодируется статусом ученика.

Поддержаны семейства numeric/literal (общий множитель) и numeric_bracket/literal_bracket (умножение на скобку). Неизвестное действие сначала требует реализации генератора и проверки; его нельзя автоматически объявлять доступной темой. В новых темах умножения уровни и граф зависимостей не назначены.

Каждый шаблон имеет устойчивый ID и revision (отсутствующая старая revision равна 1). В импортированных материалах сохранены исходные условия и SHA-256. Новая/изменённая активная запись содержит `approval`: decision=approved, approved_by, source_ref, content_sha256 и approved_at либо recorded_at. recorded_at — дата технической фиксации прежнего решения, не вымышленная дата утверждения. Хеш считается по каноническому JSON записи без approval: UTF-8, ключи отсортированы, без лишних пробелов, Unicode не экранируется. Сам receipt не доказывает человеческого согласия: чат должен иметь явное решение владельца именно по этому содержанию.

## Действия тематического чата после явного утверждения

1. Прочитать актуальные общий стандарт, этот документ и целевой каталог из main репозитория muradsatabi/math_trainer через подключённый GitHub. Сохранить SHA прочитанного файла/коммита.
2. Подготовить только согласованные записи. Связать approval с точным содержанием и источником решения; не менять другие записи и рабочие статусы без решения владельца. Повторная передача тех же ID и содержимого — без изменений, не новый набор.
3. Создать отдельную ветку codex/content-… от прочитанного main. Через GitHub create_file/update_file записать обновлённый каталог целиком с проверкой исходного SHA; не писать прямо в main. Возможны также create_tree/create_commit/update_ref с обязательными base_tree, parent и проверкой ожидаемого SHA: отсутствие base_tree недопустимо.
4. Создать Pull Request с перечнем ID, revision, источником методического решения и разделением active/deferred/review. Для локальной подготовки доступен `python tool/template_bank.py --import-package PACKAGE.json --target TOPIC.json`. Пакет содержит schema_version=1, base_content_sha256 исходного каталога и templates с утверждёнными обновлениями. Пользователь не переносит отдельные задания вручную: пакет и операции готовит чат.
5. Дождаться проверки Validate template publication на точном SHA PR: формат, ID, ссылки, версии, approval, отсутствие удаления, поддержка математики и тесты Flutter. При изменении main повторно сверить содержание; не решать методические конфликты автоматически. Слияние допускается только в пределах отдельно разрешённой владельцем политики. Наличие общей цели не отменяет правило AGENTS.md об отдельном разрешении на Git-коммит.
6. Только после принятия в main сообщить ссылку и полный SHA опубликованного коммита. Падение CI и открытый PR не являются публикацией. Новый банк попадает в следующую сборку; прежние занятия продолжают использовать свои снимки.

## Проверки и защита

`python tool/template_bank.py` проверяет формат и поддерживаемые правила без внешних Python-зависимостей. `--base-ref SHA` дополнительно запрещает исчезновение файлов/ID, изменение без новой revision и публикацию активных изменений без связанного approval. `python -m unittest discover -s tool -p test_template_bank.py` проверяет идемпотентность и конфликты. JSON Schema предназначена также для редакторов; дополнительные межфайловые и версионные правила реализованы валидатором. Flutter-тест сверяет математическое равенство каждого активного образца и допустимость формы ответа.

Все операции ограничены содержимым банка. Токены, результаты учеников и браузерное хранилище не попадают в репозиторий. История ранее опубликованных revision остаётся в Git; исправление создаёт следующую revision. Снятие шаблона с работы — изменение статуса с сохранением ID, не удаление записи.

## Проверенные доступы и незавершённая настройка

В текущем чате подключённый GitHub подтвердил права push/admin на muradsatabi/math_trainer. Это не подтверждает наличие инструментов записи в каждом методическом чате. Для завершения настройки требуется публикация инфраструктуры в GitHub и одно согласованное подключение инструкции к методическим чатам, затем контрольная передача из одного такого чата. Без этого нельзя обещать, что обычное слово «утверждаю» само вызовет GitHub.

Официальные источники: [MCP с инструментами чтения и записи](https://developers.openai.com/api/docs/guides/custom-mcp-server), [подключение и проверка плагина](https://developers.openai.com/plugins/deploy/connect-chatgpt). Настройки и подтверждения зависят от чата и workspace. Глобальные подтверждения не отключаются. При необходимости потребуется однократное действие владельца для подключения/авторизации; отдельный сервер не создаётся, пока достаточно существующего GitHub-плагина.

## Безопасное получение принятого банка локальным проектом

`python tool/sync_template_bank.py --root PROJECT` получает только JSON из bank/templates опубликованного main. Скрипт сверяет Git blob SHA, формат, версии и ID, запрещает удаление каталога и не меняет lib, документацию или .git. Локальные изменения защищены сравнением со снимком последнего применения; конфликт сохраняет все файлы. Пакет проверяется целиком до замены, ошибка применения откатывает уже заменённые файлы. Состояние находится в игнорируемой .dart_tool/template-sync.json, без результатов учеников и секретов.

Режим --watch проверяет раз в 300 секунд. Для нынешнего публичного репозитория ключ не нужен; при закрытии репозитория потребуется отдельная авторизация. Фоновый процесс запускается один раз после публикации инфраструктуры; автозапуск Windows пока не установлен. Новые данные попадают в новую сборку, а не изменяют уже открытое занятие. Закрытый ноутбук не синхронизирует проект; после запуска обработает опубликованное состояние.
